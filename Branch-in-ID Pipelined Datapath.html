Branch-in-ID Pipelined Datapath

Pipelined datapath with branch resolved in ID

The four additions in ID

  1. Shift left 2 on the sign-extended offset. The offset counts words, so ×4 turns it into a byte offset.
  2. Branch target adder computing (PC+4) + offset×4, using the PC+4 already held in IF/ID.
  3. Equality comparator (=) on Read data 1 and Read data 2. In hardware: XOR the two values bit by bit, then NOR all 32 results. It is far faster than an ALU subtract.
  4. IF.Flush from Control. When the branch is taken it zeroes the instruction in IF/ID, turning the wrongly fetched instruction into a nop.

Why the decision is ready by the end of ID

Registers are read in the first half of the cycle, so the comparator and the target adder finish within ID. Control's Branch is ANDed with the comparator output to form PCSrc, which selects the target at the PC mux. The PC loads the target at the end of ID, so only the one instruction in IF is wrong and gets flushed: a 1-cycle penalty instead of 3.

Slide 78 example, clock cycle 3

beq $1, $3, 7 at address 40 is in ID with PC+4 = 44. Target = 44 + 7×4 = 72. Since $1 = $3, PCSrc = 1 and IF.Flush = 1: the and fetched from 44 is squashed, and the next fetch is lw $4, 50($7) at 72. Tap Show slide 78 example to see these values on the wires.

What the figure leaves out

  • Forwarding paths into the comparator. The operands are now needed in ID, so slides 79–81 add stalls: 1 cycle if the source is the preceding ALU instruction or a load two back, 2 cycles if it is the immediately preceding load.
  • The RegWrite and $zero checks on the forwarding unit (slide 59 omits them too).
  • Individual EX control wires to the ALU control, ALUSrc and RegDst muxes.
